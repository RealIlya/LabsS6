# Учебная карта по лабораторным работам 3 и 4

## Назначение материала

Этот конспект помогает объяснить логику двух лабораторных работ на защите. Главная цель - не перечислить файлы проекта, а понять, какие идеи лежат за реализацией: как строится пользовательский интерфейс, где хранится состояние, как проверяются данные и почему одна и та же предметная область по-разному выглядит в веб-приложении и настольном приложении.

## 1. Общая предметная область

Обе лабораторные работы построены вокруг книжного каталога. В системе есть книги, пользователи, роли, поиск, бронирование, добавление новых записей и списание экземпляров.

С точки зрения теории это не просто набор экранов. Это модель предметной области:

- книга имеет библиографические данные и количество экземпляров;
- пользователь имеет роль и набор разрешённых действий;
- бронирование уменьшает число доступных экземпляров;
- списание изменяет общее количество экземпляров и может переводить книгу в архивное состояние;
- интерфейс должен показывать пользователю только те действия, которые имеют смысл в текущем состоянии.

Главная идея: интерфейс является способом управлять состоянием предметной области. Если состояние меняется неправильно, внешний вид программы может оставаться красивым, но логика системы будет неверной.

## 2. Предварительные понятия

### Клиент и сервер

В веб-приложении клиентом является браузер, а сервер выполняет основную C#-логику и формирует ответ. Браузер показывает HTML, CSS и JavaScript, но не должен быть единственным местом проверки правил.

Ментальная модель: браузер - это экран и источник действий пользователя, сервер - место принятия окончательных решений.

Ошибка понимания: считать, что если проверка есть в JavaScript, то серверную проверку можно убрать. Клиентский код можно обойти, поэтому сервер всё равно обязан проверять важные правила.

### Событийная модель

И Web Forms, и WinForms используют событийный стиль мышления: пользователь нажимает кнопку, выбирает строку, вводит данные, а программа реагирует обработчиком.

Разница в том, что в WinForms событие происходит внутри одного настольного процесса, а в Web Forms действие часто превращается в HTTP-запрос к серверу.

Ошибка понимания: думать, что обработчик кнопки в Web Forms работает так же прямо, как в WinForms. В Web Forms между нажатием и обработчиком есть сетевой запрос, восстановление состояния страницы и генерация нового ответа.

### Состояние

HTTP сам по себе не хранит состояние между запросами. Поэтому веб-приложению нужны механизмы сохранения контекста: например, `Session` для данных пользователя на сервере и `ViewState` для восстановления состояния элементов страницы.

В WinForms состояние обычно находится в памяти приложения: открытые формы, текущий пользователь, списки книг, бронирования и архивные записи.

Компромисс: хранить состояние удобно, но оно усложняет отладку. Нужно понимать, где именно находится актуальная версия данных.

## 3. Лабораторная работа 3: Web Forms и AJAX

### Что решает Web Forms

ASP.NET Web Forms позволяет строить веб-страницы по модели, похожей на настольные формы: есть элементы управления, события и code-behind на C#. Это удобно для форм, таблиц, каталогов и административных экранов.

Ментальная модель: разработчик думает в терминах серверных контролов и событий, а фреймворк преобразует это в HTML, JavaScript, запросы и ответы.

Компромисс: Web Forms скрывает часть веб-механики. Это ускоряет разработку, но может мешать понимать, когда реально происходит запрос, где хранится состояние и почему страница перерисовывается.

### Postback

Postback - это отправка страницы обратно на сервер после действия пользователя. Сервер восстанавливает состояние страницы, выполняет обработчик события и возвращает обновлённый HTML.

Что он решает: позволяет писать обработчики серверных событий для веб-страницы.

Что ломается при непонимании: можно случайно выполнять тяжёлую логику при каждом запросе, терять введённые данные или неправильно обновлять элементы после частичной перерисовки.

### AJAX

AJAX нужен для асинхронного обмена данными между браузером и сервером без полной перезагрузки страницы. Пользователь получает более отзывчивый интерфейс: например, результаты поиска, статус бронирования или проверка поля могут обновляться сразу.

Ментальная модель: запрос всё равно уходит на сервер, но браузер обновляет только нужный фрагмент интерфейса.

Компромисс: интерфейс становится удобнее, но появляется асинхронность. Ответы могут приходить с задержкой, действия могут повторяться, а часть логики оказывается распределена между JavaScript и сервером.

### UpdatePanel

`UpdatePanel` позволяет сделать частичное обновление страницы в стиле Web Forms. Разработчик сохраняет серверную событийную модель, но пользователь не видит полной перезагрузки страницы.

Что он решает: уменьшает визуальные сбросы страницы и делает старую Web Forms-модель более плавной.

Ограничение: это не превращает приложение в SPA. Серверная модель остаётся прежней, а частичное обновление всё равно может передавать больше данных, чем ручной точечный AJAX-запрос.

### PageMethods и обработчики

`PageMethods` и отдельные HTTP-обработчики позволяют вызывать серверную логику из JavaScript. Это удобно для точечных проверок: например, проверить занятость email или уникальность ISBN до отправки всей формы.

Ментальная модель: JavaScript спрашивает сервер о конкретном факте, сервер возвращает короткий ответ, интерфейс показывает результат.

Ошибка понимания: воспринимать такую проверку как окончательную. Она улучшает UX, но при сохранении формы сервер всё равно должен проверить данные повторно.

### Валидация

В лабораторной работе используются серверные и клиентские проверки: обязательные поля, диапазоны чисел, регулярные выражения, сравнение значений и динамические ограничения.

Что решает валидация: не даёт системе перейти в некорректное состояние.

Ментальная модель: проверка должна стоять как можно ближе к месту риска. Клиентская проверка помогает пользователю, серверная защищает данные.

Типовая ошибка: проверять только формат, но не проверять бизнес-правило. Например, корректный ISBN может быть уже занят, а корректное число списания может превышать доступное количество.

## 4. Лабораторная работа 4: WinForms-приложение

### Что решает WinForms

WinForms используется для настольных приложений Windows. Интерфейс состоит из форм, кнопок, таблиц, полей ввода и диалоговых окон. Пользовательские действия обрабатываются событиями внутри приложения.

Ментальная модель: приложение работает как управляемый набор экранов, где каждая форма отвечает за отдельный сценарий.

Компромисс: писать простые интерфейсы быстро, но при росте приложения легко смешать логику интерфейса, проверки и работу с данными.

### Формы и сценарии

Каждая форма обычно представляет один пользовательский сценарий: вход, регистрация, просмотр каталога, добавление книги, бронирование, списание, просмотр своих броней.

Что это решает: пользователь не видит всю систему сразу, а проходит через понятные шаги.

Ошибка понимания: считать форму самостоятельной программой. На практике формы должны работать с общей моделью данных и согласованными правилами.

### Общий слой данных

В лабораторной работе общий слой данных хранит книги, пользователей, бронирования, записи списания и текущего пользователя. Это упрощает проект: все формы обращаются к одному источнику состояния.

Ментальная модель: формы являются интерфейсом, а общий слой данных является памятью приложения.

Компромисс: такой подход прост для учебной работы, но в реальной системе потребовались бы база данных, разграничение ответственности, обработка конкурентного доступа и защита паролей.

### Роли и права

В системе есть роли: гость, обычный пользователь и администратор. От роли зависит доступность действий: поиск доступен всем, бронирование - пользователям и администраторам, добавление и списание - администратору.

Что решает модель ролей: ограничивает действия пользователя и делает интерфейс понятнее.

Важное различие: скрыть кнопку - это удобство интерфейса, а не полноценная защита. Настоящее правило должно проверяться в логике действия.

### Поиск и обновление таблицы

Поиск работает через фильтрацию списка книг по параметрам. После изменения данных таблица должна обновляться: после добавления, бронирования, списания или восстановления книги.

Ментальная модель: таблица - это отображение текущего состояния, а не само состояние.

Ошибка понимания: изменить данные, но не обновить представление. Тогда пользователь увидит старую картину и может выполнить неверное действие.

### Бронирование

Бронирование уменьшает количество доступных экземпляров и создаёт запись о связи пользователя с книгой.

Что решает бронирование: фиксирует намерение пользователя взять книгу и предотвращает выдачу большего числа экземпляров, чем есть в наличии.

Что ломается при ошибке: если уменьшить доступное количество, но не создать запись брони, система потеряет причину изменения. Если создать бронь, но не уменьшить количество, одну и ту же книгу можно будет забронировать слишком много раз.

### Списание и архив

Списание уменьшает общее количество экземпляров. Если списаны все экземпляры, книга перестаёт быть доступной в основном каталоге. Архивная запись нужна, чтобы сохранить факт списания и при необходимости восстановить книгу в допустимый период.

Ментальная модель: списание - это не удаление строки, а изменение жизненного состояния объекта.

Компромисс: архив усложняет модель, но делает действие обратимым и объяснимым.

## 5. Сравнение лабораторных работ

Лабораторная 3 показывает, как построить веб-интерфейс с частичными обновлениями. Главная проблема там - сетевое взаимодействие, postback, асинхронные запросы и сохранение состояния между HTTP-запросами.

Лабораторная 4 показывает, как построить настольное приложение. Главная проблема там - организация форм, событий, общей памяти приложения и согласованного обновления интерфейса.

Общее между ними: предметная область одна и та же, поэтому бизнес-правила похожи. Отличается не смысл операций, а среда исполнения и способ взаимодействия с пользователем.

## 6. Что важно сказать на защите

1. В третьей лабораторной AJAX не заменяет серверную часть, а делает взаимодействие с сервером менее заметным для пользователя.
2. `UpdatePanel` сохраняет модель Web Forms, но позволяет обновлять только часть страницы.
3. Клиентская проверка нужна для удобства, серверная - для корректности и безопасности.
4. `Session` хранит пользовательский контекст на сервере, а `ViewState` помогает восстановить состояние страницы между postback-запросами.
5. В четвёртой лабораторной WinForms работает по событийной модели внутри настольного приложения.
6. Роли нужны для ограничения доступных действий и упрощения интерфейса.
7. Таблица в интерфейсе не является источником истины, она только показывает данные из модели.
8. Бронирование и списание должны менять связанные значения согласованно: количество экземпляров, доступность и архивные записи.

## 7. Типовые вопросы и краткие ответы

### Что такое AJAX?

AJAX - это способ обмена данными между браузером и сервером без полной перезагрузки страницы. Он делает интерфейс более отзывчивым, но не отменяет серверную проверку данных.

### Чем AJAX отличается от обычного postback?

При обычном postback обычно обновляется вся страница. При AJAX-запросе обновляется только нужная часть интерфейса или выполняется точечная проверка.

### Зачем нужен `UpdatePanel`?

`UpdatePanel` нужен для частичного обновления страницы в ASP.NET Web Forms. Он позволяет оставить серверные обработчики событий, но уменьшить видимые перезагрузки интерфейса.

### Почему нельзя полагаться только на JavaScript-валидацию?

JavaScript выполняется на стороне клиента и может быть отключён или обойдён. Поэтому важные правила должны проверяться на сервере или в основной логике приложения.

### Что такое `Session`?

`Session` - это серверное хранилище данных конкретного пользователя между запросами. Например, через него можно хранить сведения об авторизованном пользователе или параметры поиска.

### Что такое `ViewState`?

`ViewState` - механизм Web Forms для восстановления состояния элементов страницы между postback-запросами. Он помогает серверной странице помнить значения и промежуточные шаги.

### Чем WinForms отличается от Web Forms?

WinForms - настольная технология: формы и события работают внутри Windows-приложения. Web Forms - веб-технология: действия пользователя проходят через HTTP-запросы к серверу.

### Зачем нужны роли пользователя?

Роли определяют, какие действия доступны пользователю. Это упрощает интерфейс и защищает операции, которые должны выполнять только определённые категории пользователей.

### Почему скрытие кнопки не равно защите?

Скрытие кнопки улучшает интерфейс, но правило доступа должно проверяться в логике операции. Иначе действие может быть вызвано другим способом.

### Что происходит при бронировании книги?

Система проверяет пользователя и доступность книги, уменьшает число доступных экземпляров и создаёт запись бронирования.

### Что происходит при списании книги?

Система проверяет выбранную книгу, причину и количество, уменьшает общее число экземпляров и создаёт архивную запись о списании. Если экземпляров не осталось, книга перестаёт быть доступной в основном каталоге.

### Зачем нужен архив списаний?

Архив хранит историю списаний и позволяет восстановить книгу, если это разрешено правилами. Он делает операцию списания контролируемой, а не просто удалением данных.

## 8. Частые ошибки в объяснении

- Говорить, что AJAX работает без сервера. На самом деле сервер обычно участвует, просто страница не перезагружается полностью.
- Называть `UpdatePanel` полноценным SPA-подходом. Это частичное обновление в рамках Web Forms.
- Считать клиентскую валидацию достаточной. Она удобна, но не является надёжной защитой.
- Путать состояние интерфейса и состояние данных. Выбранная строка в таблице - это только представление, а не сама книга.
- Объяснять роли только через видимость кнопок. Роль должна ограничивать саму возможность действия.
- Считать списание удалением. В корректной модели это изменение состояния и запись в архив.
